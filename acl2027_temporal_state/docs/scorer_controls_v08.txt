Scorer technical control, v0.8
============================

Purpose and status
------------------
The v0.7 pilot changed 26/32 support-score signs across two answer-display
conditions. Its fixed paired request schedule reused prompt prefixes, so
wording changes and numerical cache/batch history were not separately
controlled. This v0.8 experiment is a follow-up technical diagnosis designed
after seeing those aggregate development results. It is not an independent
test, evidence of accuracy, a new NLP method, or a general order-bias result.

The executable result and completion status live in
results/scorer_controls_v08.json and results/scorer_controls_v08_receipt.json.
The fixed procedure below was written before collection. The following
outcome section was appended after collection and offline verification.

Observed outcome, appended after completion
------------------------------------------
All sixteen distributions completed in eight fresh processes with no failed
attempt, replacement, retry or protocol amendment. All cold and warm input
accounting checks passed. Elapsed collection time was 1584.027 seconds
(26.400 minutes), including process setup and teardown.

Cold scores, in natural-log odds of Yes against No:
  item   kind         yes_no        no_yes        no_yes minus yes_no
  s0001  link          5.601485     -0.516766        -6.118250
  s0003  unresolved    4.386419     -2.174889        -6.561308
  s0004  reading       7.010147     -1.121359        -8.131506
  s0006  no_link       3.095415     -0.115681        -3.211096

All four cold comparisons changed score sign. All eight immediately repeated
same-prompt cold/warm pairs had exactly zero difference in the reported label
log probabilities, satisfying the fixed 1e-6 tolerance. Thus prefix carryover
is not sufficient to explain the four observed display-order differences.
This conclusion does not extend to unmeasured items, other cache histories,
hardware, models, or source histories. Literal-label probability mass ranged
from 0.9977202215 to 0.9999902593; that is not factual accuracy or calibration.

The complete result regenerated byte-identically from retained observations
without any model execution: SHA256
ce4e5ca96b592f31d04040b9c5c2654254b9bcf76f248eccfda15f0347091e31.
results/scorer_controls_v08_replay_identity.json records that check. This

These measurements diagnose the existing tiny scorer; they do not authorize
replacing v0.7 scores, averaging prompt variants post hoc, reporting accuracy,
or claiming a joint-decoding improvement. The prospective data and scoring
validation requirements below remain unfulfilled by this control.

Frozen selection and execution
------------------------------
The immutable v0.7 request defines 32 items. Take the first original-order
item of each kind: s0001/link, s0003/unresolved, s0004/reading, s0006/no_link.
The selection rule does not inspect item-level scores. Every selected item
receives both exact original prompts, whose labels keep their meanings:
yes_no and no_yes. Their input lengths are respectively 5759, 5257, 5269,
and 7856 tokens for either condition. No shorter replacements are allowed.

For every item/condition, start a fresh owned llama-server process. The first
model completion uses cache_prompt=false. Immediately repeat the identical
full token array with cache_prompt=true. Terminate that process before the
next condition. This gives eight fresh processes and sixteen distributions.
First-condition order alternates by selected item: yes_no first for s0001
and s0004, no_yes first for s0003 and s0006. This balance is deterministic,
not randomization, and does not make four items independent observations.

The cold response must report cache_n=0 and prompt_n=full input length.
The warm response must report a positive reused prefix. Both must report
cache_n+prompt_n=full input length, tokens_evaluated=full length,
tokens_predicted=1, and truncated=false. Model weights, llama.cpp files,
native template, rendered prompt bytes, token IDs, exact one-token label
boundaries, and frozen input hashes are checked. A cache_prompt setting by
itself is not accepted as proof of cold or warm execution.

The same Qwen3-0.6B Q8_0 weight artifact and llama.cpp b11146 runtime used in
v0.7 are used without downloads or fallback. Each process has the frozen
8192-token context, four CPU threads, Q8 KV cache, batch256/microbatch128,
flash attention, 2GiB address-space hard limit, and 2250 CPU-second hard
limit. Eight process limits sum to 18000 CPU seconds. Runtime properties,
execution bindings, process logs and full top256 responses are retained.
This runtime is pinned by files and settings, not a hermetic container.

Neither prompt content nor backend likelihood semantics change. The score
is natural-log P(Yes)-natural-log P(No), taken at the identical unconstrained
next-token position from full-vocabulary probabilities. Both label log
probabilities and their total literal-label mass are retained. No label-only
normalization, logits bias, grammar, calibration, prompt averaging or decoder
replacement is introduced. v0.7 remains the frozen primary pilot.

Freeze and reproduction
-----------------------
configs/scorer_controls_v08.json records the fixed procedure.
data/scorer_controls_v08/frozen_inputs.json binds the collector, configuration,
v0.7 prompt and token records, request, backend configuration, source code,
template binding, and full-vocabulary probability evidence before scoring.
executed_collector.py.txt preserves the source that actually ran. The
collector writes its started receipt before creating a server and retains
every completed raw response before validating it. An error aborts the run
without retries, substitutions or score-based item removal.

Offline verification, without model execution or network calls:
    python scripts/scorer_controls_v08.py

The --prepare and --collect flags were used once to freeze and collect the
canonical run. They refuse to overwrite existing frozen or attempted work.
Do not delete canonical evidence to rerun them. A future actual regeneration
should use a separate project copy that omits data/scorer_controls_v08 and
results/scorer_controls_v08*.json while retaining the archived original
checkpoint. In that fresh copy, run --prepare and then --collect with
--assets set to the absolute path of the verified external asset directory.
Retain both runs; the collector intentionally has fixed destinations within
its own project copy, not an output-directory override.
The external assets can be obtained and verified with the existing v0.7
asset bootstrap. Asset downloads are never triggered by offline verification.

Comparisons and their limits
---------------------------
The result retains all sixteen measured rows, then reports for every item:
  * cold no_yes minus cold yes_no log-odds;
  * warm no_yes minus warm yes_no log-odds;
  * their difference, a conditional interaction diagnostic;
  * warm-minus-cold differences for each label and log-odds within each prompt;
  * cold display-order sign changes.

The fixed numerical tolerance is 1e-6 on each of the two label log
probabilities. Passing a warm repeat does not prove all prompt histories,
all hardware or other models are numerically identical. A fresh process
controls prompt KV carryover; it does not reset the operating system's file
cache or turn system scheduling into a randomized treatment. Wall times are
execution costs, not a fair hardware benchmark.

If cold display-order differences remain, cache carryover is not a sufficient
explanation of those four observed differences. That would not establish
that cache history contributed nothing to v0.7's other 28 items. The two
prompts differ in how answer labels are displayed; broader prompt sensitivity,
task ambiguity, poor instruction following, and model calibration remain
possible contributors. No statistical significance or population estimate is
computed from the dependent items in this one history. No gold data are loaded.

Prospective validation on newly annotated source histories
---------------------------------------------------------
Before treating any scorer as suitable for the paper, capture and annotate
the separate source-stream development frame using the frozen delivery-prefix
protocol. Keep document availability, delivery, publication and event times
separate. Freeze source groups before candidate generation; preserve excluded
and difficult cases. Do not select cases by whether joint decoding wins.

For a subsequent scoring comparison, preregister a history-level split with
development and held-out source groups, the annotation rubric, admissible
abstention labels, conflict resolution and blinded adjudication. Human or
independent adjudicated references should distinguish source support from
current-world truth. Multiple dependent candidate options from a history
must not be treated as independent examples for uncertainty estimates.

Use separate data to choose any scoring template or calibration. On frozen
evaluation histories, measure discrimination, abstention behavior, label
mass, calibration where a probability claim is intended, and sensitivity to
fixed semantically equivalent prompt variants. Compare the tiny pilot with a
resource-feasible stronger pinned scorer only when its runtime and access are
available. Repeated prompt orders may be a preregistered robustness procedure,
not a post-hoc choice of the answer producing a favorable decoder outcome.

Finally compare independent, ordinary iterative, restart and joint methods
with identical candidates and scores. Report optimization gaps separately
from source-grounded state/question accuracy and correction propagation.
The current control supplies none of these held-out accuracy measurements.
