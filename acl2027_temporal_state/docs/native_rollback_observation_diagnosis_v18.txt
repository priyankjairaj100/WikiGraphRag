Read-only diagnosis of the v18 rollback-observation failure

Conclusion

The failed v18 gate did not observe nonzero rollback state. It observed no
n_rs_seq field. The pinned runtime's logging policy explains this absence:
llama_context emits the actual cparams.n_rs_seq at LLAMA_LOG_INFO, while the
common callback maps GGML INFO to TRACE verbosity 4. The server's default
threshold is 3, exactly as recorded in the retained v18 server log. Library
INFO messages, including context and cache allocation lines, are filtered before
being queued. Server/common INFO messages remain visible at threshold 3.

Defaults and API limits

The pinned context API default n_rs_seq is zero. Common initialization sets it
from params.speculative.need_n_rs_seq(); this returns zero unless selected
draft methods require rollback snapshots. That is a source-level derivation,
not an observation of the terminated process. Config/environment/CLI can affect
parameters, so the default alone should not replace the frozen observation gate.

The pinned API has llama_n_rs_seq(ctx), which directly reads cparams.n_rs_seq,
but no such context getter is exposed by the existing /props response. Its
get_res_props implementation constructs task_params and copies sampling values;
it intentionally avoids accessing the live server context. The returned
speculative.types='none' therefore cannot serve as an authoritative measurement
of actual allocated rollback state. No new endpoint or library injection is
needed for the narrower logging remedy.
