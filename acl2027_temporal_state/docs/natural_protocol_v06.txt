NATURAL CANDIDATE AND SCORE PROTOCOL v0.6

Purpose and current boundary
----------------------------
Move from singleton migration / authored scores to multiple source-grounded
candidate readings and model judgments, with one frozen candidate/score artifact
shared by every decoder. This file specifies an experiment protocol. It does
not claim calibrated scores, extraction correctness, an algorithmic advantage,
or completed pinned-model execution. The exploratory conversational pilot has
separate raw outputs and receipts in data/natural_model_pilot_v06; consult that
directory's current run record for execution status.

The old source_extractor_v0.3 schema already allowed several candidates with the
same mention_id. The missing parts were scored alternative graphs, conditional
link alternatives, uncertainty as an explicit decoder choice, and correction
evidence. Its prompt explicitly sent corrections to unresolved. Existing
singleton migrated claims are therefore not evidence that a model considered
and scored alternatives. All prior prompts/configs and prior natural annotations
remain unchanged by this protocol work.

Files and callable interfaces
-----------------------------
configs/candidate_prompt_v06.txt and candidate_schema_v06.json specify a
question-free graph with mentions, mutually exclusive readings, candidate links,
aliases, source authorities, essential support dependencies and unsupported
items. Each mention permits zero to four resolved readings; the adapter adds
one unresolved option. Source evidence uses exact unique quotes, with offsets
computed by validation rather than generated by the model.

scripts/prepare_natural_protocol_v06.py:
  build_requests() -> config, artifact hashes, source-pack hashes, requests
  pilot_request(config, requests) -> one prespecified small source request
  --manifest PATH writes a source-text-free provenance manifest.
  --emit-pilot PATH additionally writes the exact source request.
It reads only versioned protocol inputs and the two previously pinned source
packs. It does not read old annotations, questions, expectations or results.

scripts/validate_candidate_graph_v06.py:
  validate_graph(raw_string, source_request_dict) -> alignment / integrity report
Checks strict schema, duplicate IDs, source hashes, eligible prefix, exact unique
quotes, primary anchor overlap, endpoint references, supported correction
certificate structure, source attribution, essential dependency cycles and basic
temporal consistency. It reuses the existing v0.3 schema/bounds primitives.
It never repairs evidence or silently drops a candidate. Final bounded claim,
correction-policy and scored-cache validators remain additional required gates.
Exact quotes, declared authority and schema validity do not certify entailment.

scripts/prepare_ordinal_scoring_v06.py:
  prepare(source_request_dict, candidate_raw_string) -> scoring_request, manifest
  validate_scores(raw_score_string, scoring_request_dict) -> validation report
The preparation function validates candidates first, strips generation notes,
unresolved rationales and original candidate IDs, then assigns opaque scoring
IDs in a deterministic order based on hashes of neutral content. Its manifest
maps each ID to the exact original mention/candidate/link. All sources shown to
the generator remain scorer context, irrespective of which are quoted.
It makes explicit reading, unresolved, link and no_link items. The output gate
requires one integer judgment for every item; omitted null/unresolved judgments
are never replaced with convenient constants. No model runs inside the builder.

Input construction and prefix discipline
---------------------------------------
The builder reproduces three independent history-prefix requests:
  leadership_starbucks_2024 at 2024-08-15
  leadership_nike_2024 at 2024-09-20
  leadership_starbucks_2024 at 2024-11-21
No request sees a different history, a later source, an earlier model response,
or any query/answer. Every source-pack file hash, source-text hash, request hash,
prompt and schema hash is recorded. Duplicate keys, changed hashes, undeclared
histories, extra source-pack fields and future sources fail rather than filter.

These are operational development cutoffs inherited unchanged from the old
source packs. In particular, next-calendar-day-after-SEC-acceptance is not a
verified historical first-public-availability timestamp. This protocol does not
retroactively authenticate the captured historical source version. The separate
Lyft capture has a different evidence trail and is not silently added here.

The source-only exploratory pilot scopes the Nike prefix to Nike CEO occupancy,
appointment and departure. It excludes separate President, Board, adviser and
employment claims while retaining their surrounding source text. It merges
repeated wording within a source only for an identical atomic proposition and
preserves distinct sources as distinct mentions. Limits are eight mentions and
four resolved readings per mention; overflow fails without score/gold pruning.
This is a manually selected development case: source inspection identified
different departure-date wording in the two eligible documents. It is not a
random sample or an untouched held-out benchmark. Alternatives are not required
when the source supports only one reading. The schema must not manufacture
ambiguity to make joint decoding look useful.

The durable pilot request is a byte-for-byte copy of the emitted temporary
request, in data/natural_model_pilot_v06/candidate_request.json. It duplicates
already supplied source texts only; no additional captured full documents are
redistributed. source_capture raw-file exclusions from v0.5 remain applicable.

Candidate semantics and compatibility
-------------------------------------
One reading is a faithful interpretation of a historical assertion. It may be
faithful even when the assertion was erroneous and later explicitly corrected.
Later eligible context can help resolve reference but cannot rewrite old claims.
Correction links determine active support separately from reading faithfulness.

Current representation is deliberately restricted. Dates are bounded daily
endpoints of one connected half-open interval. Fiscal-year scope alone is not
an event date. Future plans do not establish occurrence. CHANGES only represents
the implemented positive functional succession semantics; an arbitrary change
in a numeric forecast must not be mislabeled CHANGES. CORRECTS supports whole
assertion replacement by the same declared authority. Partial-field repair and
pure retraction remain unsupported.

A separate correction notice and replacement exhibit need an explicitly
documented composite source to meet the current same-source reference-span
contract. The extractor cannot silently invent that composite. Essential support
dependencies require explicit provenance language; RESTATES is not copying, and
the absence of a dependency record does not prove independent corroboration.

Important first-pass compatibility observation: the candidate schema exposes
observation_kind=mixed, but the inherited temporal validator rejects any
announced_future reading containing actual state observations. The original
v0.6 extraction prompt did not state that full restriction clearly enough.
The first exploratory output failed with plan_with_actual_state_observation.
Its raw output and failure receipt are preserved; no validator was relaxed and
no score was generated for that invalid candidate graph by this preparation
path. Any validation-only repair must be a separately hashed request/output
with the exact validation failure recorded. It is a development correction to
the protocol/output, not a clean first-pass extraction success. Separating a
current occupancy assertion from a future departure is a representation choice
that must preserve provenance, not a license to change dates or infer outcomes.

One repair is now explicitly prepared in candidate_prompt_v06_repair.txt,
candidate_schema_v06_repair.json and validation_repair_protocol.json. The repair
prompt clarifies the generic restrictions without giving dates, IDs or answers.
Its standard JSON Schema uses if/then to require empty observations on planned
readings. The current custom structural validator does not parse those new
keywords: validate_graph intentionally validates the unchanged original shape,
then the existing explicit temporal check enforces that same restriction. Do
not claim that the custom engine implements general JSON Schema conditionals.
Original prompt, schema and raw output are preserved. Any accepted repair is
an additional extraction attempt and its cost/failure must remain in reporting.

Exploratory ordinal scoring
---------------------------
configs/scorer_ordinal_prompt_v06.txt and scorer_ordinal_schema_v06.json are the
direct fresh conversational scorer contract. Each option receives an integer
from -3 to +3: explicit contradiction at -3, neutral/balanced evidence at 0,
explicit unambiguous support at +3, with intermediate qualitative anchors.
The model judges unresolved and no_link explicitly using their stated abstention
semantics. Link judgments condition on the two endpoint readings being admitted.
The supplied text and neutral candidate structures contain no generation notes,
previous scores, chosen decoder state or expected answer. The source request's
complete context and filtering rule remain visible.

This is one fresh scorer context containing all atomic items. Fresh context does
not establish statistical independence between judgments, model-family
independence from the extractor, or absence of pretraining knowledge. Same-family
extraction/scoring may share biases. The score meanings explicitly concern source
interpretation, not final truth, current activity or answer correctness.

The additive decoding objective treats these ordinal values as a prespecified
heuristic with beta=1 and no added penalties. An ordinal scale has no guaranteed
cardinal spacing: applying another monotone mapping can change an additive
optimum. Therefore report score scale, null/unresolved judgments, ties, objective
decomposition and sensitivity before making substantive performance claims.
Do not relabel these judgments as token likelihoods, probabilities or calibrated
confidence. A no_link potential is shared across readings of a mention under
the existing decoder; it is not a fully conditional probabilistic no-link model.

The cache's unversioned_model_scores provenance must use explicit candidate and
scorer IDs and null revisions, with the bound prompt/config hashes. It cannot
use pinned_model_scores. Conversational receipts retain the exact task, visible
input files, raw output, schema, validation and any repair. The general protocol
does not imply that the conversational execution has an immutable model build.

Future pinned likelihood scorer
------------------------------
configs/scorer_prompt_v06.txt instead defines an atomic SUPPORTED versus
INSUFFICIENT decision. scorer_schema_v06.json describes a RUNNER-generated
record, not the model's JSON response. A supported backend must teacher-force
the exact two label continuations under the same prompt and repeat with label
meanings swapped. Record exact input/continuation token IDs and every conditional
log probability. Never use sampled-token confidence as the missing alternative
likelihood, and never ask a model to invent likelihood numbers.

For each permutation p, compute d_p = logP(supported continuation | input_p)
minus logP(insufficient continuation | input_p); score is their mean. This
reduces label-name bias but does not prove calibration. Verify tokenization and
continuation boundary treatment; preregister exact continuation strings and any
handling of unequal token lengths. Use no length normalization chosen after
observing outcomes. Reject truncated or incomplete records. Log probabilities
must be finite, nonpositive and sum to each sequence log probability. All four
label records must be present. The current schemas describe these data; the
model execution/likelihood collector is not implemented by the preparation
scripts and no such values have been collected here.

For that future branch, unresolved and no_link are prespecified zero reference
potentials, with calibrated thresholds or penalties, if needed, fitted only on
a separate development split before the evaluation freeze. This differs from
the exploratory ordinal branch's explicitly judged null options. Never combine
the branches without recording the objective change. Their potential functions
are uncalibrated evidence compatibility scores until an independent calibration
study establishes more. The sum is not automatically a joint log posterior.

Required artifact and validation sequence
-----------------------------------------
1. Freeze a question-free source request, source IDs/hashes, scope/admission rule,
   availability convention, prompt, schema, runtime and decoding settings.
2. Extract in an isolated context; preserve raw output and termination status.
3. Validate without evidence repair or label-driven pruning. Record every failed
   attempt; any retry is separately bounded and disclosed.
4. Build neutral atomic score requests from accepted candidates. Freeze their
   digest and the scorer contract before executing a fresh scorer.
5. Validate exact coverage, finite numeric/ordinal semantics and exact evidence.
   Preserve all raw judgments, including those later judged wrong.
6. Adapt once to claims, sources, aliases and correction policy. Propagate every
   visible source into context provenance. Freeze a shared scored cache before
   invoking exact, independent, iterative or restarted decoding.
7. Run each algorithm against exactly that cache and semantics. The current small
   search budget is not a scalable algorithm claim. Report inability to run any
   method rather than selecting an easier candidate subset based on results.
8. Only then load a separately frozen evaluation artifact, if one exists.
   A source-only replay without such labels measures no answer accuracy.

Research gate for a publishable result
-------------------------------------
The current small development sources can expose implementation failures and
natural ambiguities. They cannot establish natural generalization. The needed
study has held-out histories, adjudicated source evidence/candidate coverage,
multiple independent histories per update type, robust actual-versus-plan and
correction controls, frozen scorer/objective settings, and paired comparisons
of methods on identical candidate sets. Measure extraction/candidate recall,
unsupported and invalid rates, scored alternative quality, end-to-end answers,
abstention and calibration separately from optimization correctness. Gains that
come solely from an alternate score function or more candidate coverage must
not be attributed to a better search algorithm. Source availability/version
uncertainty and the known development repairs remain explicit limitations.
